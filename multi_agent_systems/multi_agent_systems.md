# Multi-Agent Systems: What's Actually Working

**Source:** [Multi-Agents: What's Actually Working (Cognition AI)](https://cognition.ai/blog/multi-agents-working)

## Core Philosophy
* Context engineering is more durable than prompt engineering. The focus should be on giving the right context to models, assuming they become more capable over time.
* Most multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions. Parallel writers make implicit choices that often conflict.
* The open problems in multi-agent systems are primarily communication problems: escalation timing, surfacing sibling discoveries, and context transfer without drowning the receiver.
* Unstructured swarms (arbitrary networks of agents negotiating) are mostly a distraction.

## The Generator-Verifier Loop (Code-Review-Loop)
* Having a model review its own code (or code generated by a peer agent) works exceptionally well. It often catches severe bugs (logic errors, missing edge cases, security vulnerabilities).
* **The Clean Context Advantage:** This technique works best when the coding and review agents do not share any context beforehand.
  * A clean context forces the review agent to reason backward from the implementation without the spec, allowing it to openly question overlooked aspects.
  * It combats **Context Rot** (models making less intelligent decisions at longer context lengths due to limited attention heads). By skipping extraneous context (history of the coder's work, searches, etc.) and only looking at the diff, the reviewer maintains improved intelligence for nuanced issues.
* **Communication Bridge:** Crucial for success is how the primary agent synthesizes the reviewer's feedback with the broader context (user instructions, decisions) to filter bugs, preventing infinite looping or out-of-scope work.

## The "Smart Friend" Pattern (Capability Escalation/Routing)
* **Goal:** Achieve frontier-level capabilities at lower cost and faster speeds by pairing a primary (smaller or faster) model with a "smart friend" (larger, more capable) model.
* **Small-to-Large Setup:** The primary model decides when a situation is tricky enough to consult the smarter model.
  * *Challenges:* The core trickiness is how a dumber model knows it's at its limits. Solutions include prompting the primary to always make at least one call to evaluate, or prescriptive guidance (e.g., always escalate merge conflicts).
  * *Context Sharing:* A reasonable 80/20 solution today is to share a fork of the primary's full context with the smart model.
  * *Bidirectional Communication:* The smart friend must know how to talk back. If context is missing, it should instruct the primary to investigate and report back, rather than guessing. An "over-scoped" smart friend that provides guidance beyond the immediate question leads to better interactions.
  * *Current State:* Asymmetrically weaker primary models often struggle to know when to escalate. This is likely a training problem for future models.
* **Cross-Frontier Setup:** Using two strong models (e.g., Claude and GPT) together. Here, delegation acts as a capability router rather than a difficulty escalator (routing to whichever model is best at specific sub-tasks like debugging, visual reasoning, or testing).

## Higher-Level Delegation (Map-Reduce-and-Manage)
* Extending the single-writer/multi-intelligence paradigm to larger scopes (e.g., features spanning multiple PRs).
* **Architecture:** A manager agent splits work, spawns child agents to execute, then synthesizes and reports back.
* **Context Engineering Challenges:**
  * Managers trained on small scopes default to being overly prescriptive, backfiring without deep codebase context.
  * Child agents often assume they share state with siblings or parents when they don't.
  * Cross-agent communication (children messaging the manager to inform siblings) doesn't happen by default and requires dedicated prompting or training.
